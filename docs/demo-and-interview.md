# 五分钟演示与面试讲解

## 运行与观察

先按[README](../README.md#快速运行)安装并启动，建议系统Chrome/Edge中分开打开顾客端与管理端。若聊天内置浏览器一直转圈，不把该现象等同于业务验证成功；本次仍保留该视觉复验待办。

1. 顾客用演示手机号与验证码登录，查看区域价格并选空闲座位上机；管理端观察座位变化。
2. 顾客购买茶饮，管理端依次履约，顾客通过现有页面刷新/查询观察状态。订单实时推送尚未接入。
3. 顾客为当前座位报修，管理端观察新工单并接单。可选择换至空闲机器，原机器继续待维修；随后完成原机维修。
4. 顾客申请下机，观察账单、交易流水和保洁任务；管理端完成保洁，座位恢复空闲。演示会修改本地数据，不对接真实支付。
5. 解释失败路径：欠费固定账单、同请求重试、其他会员访问拒绝、推送断开后的快照恢复。相关边界优先展示隔离测试，避免为演示直接改数据库余额。

已有操作实拍见[历史仿真手册](06-local-simulation.md)。顾客换机后的会话主动补偿尚未接入，不宣称此部分已做到无感更新。

## 推荐讲解顺序

| 问题 | 代码入口 | 应讲清楚的取舍 |
| --- | --- | --- |
| 重复点击为何不会重复充值/点单？ | billing.service、order.service及对应请求DTO | 请求键、内容一致性、结果查询；不夸大跨实例保证 |
| 扣款与流水如何保持一致？ | local-transaction、billing.service | 事务提交/回滚，SQLite队列的进程边界 |
| 余额不足为什么不持续涨费？ | Session的settlementRequestedAt | 首次申请固定账单，补款重试，座位仍占用 |
| 顾客会收到其他人的工单吗？ | SocketPolicy、EventsGateway | 服务端房间、真实报修人、发送前身份重查 |
| 换账号和重连为何不覆盖新数据？ | frontend stores/socket、machine、fault | 身份/请求版本、订阅ack顺序、在途事件合并 |
| 如何证明失败时不会误发成功事件？ | socket-authorization.e2e-spec.ts | 真HTTP+Socket、内存库、事务后段故障注入 |

## 简历素材（按本人实际贡献改写）

> 基于Vue 3、TypeScript、NestJS与TypeORM实现双端网吧服务演示系统，覆盖选座计费、茶饮订单、故障换机及保洁流程；通过事务、请求幂等与结果查询处理重复提交及超时确认，并完善员工岗位权限、会员字段白名单与操作者记录。

> 为Socket.IO增加JWT鉴权、岗位/本人授权订阅和提交后工单通知，管理端重连通过HTTP快照与在途事件合并恢复列表；使用隔离SQLite与真实HTTP/Socket回归验证权限、回滚及通知边界。

不要填写未经压测的QPS/并发数、未经度量的性能提升比例或虚构真实用户与营收。测试项数可引用[验证报告](validation-report.md)，但不将其称为生产覆盖率；团队项目和历史代码应如实说明个人负责部分。
