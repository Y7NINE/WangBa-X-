# 订单请求与结果确认

当前水吧订单使用账户余额记账，不调用真实在线支付。员工端现有页面负责查看与履约，顾客端负责浏览菜单、创建订单和确认配送进度。

## 创建订单

`POST /orders` 允许顾客及店长、经理、收银。请求示例：

```json
{
  "requestId": "a03f9fd2-24e9-4ba7-883c-a3760f9c8b15",
  "items": [{ "itemId": 5, "qty": 1 }],
  "remark": "送到座位即可"
}
```

员工代客下单须额外提供有效 `userId`；顾客会员ID始终取登录身份，不能用此字段替换为他人。请求编号必须为UUID v4，服务端统一为小写；超时重试必须使用原编号和原参数。新格式只接受商品编号、数量和可选备注，不再接受旧版JSON字符串明细、客户端名称/单价/总价或配送座位。商品按服务端菜单定价，座位取会员当前active/paused上机会话；会员须可用且余额足够。

商品1–30种，每种1–20份，同种商品须合并，不接受重复条目；备注最多255字。服务端按商品编号排序，使用有效会员、商品数量和备注计算请求指纹。

- 同编号、同参数、同提交者：返回原订单，不再次扣款。商品顺序不同仍视为同一参数，返回状态可能已进入制作、完成或取消。
- 同编号改变商品、数量、备注、有效会员或提交者：409；非法请求字段和参数为400。
- 同编号重试不重新定价，也不要求会员仍在原座位；原单成功后即使菜单改价、下机或订单取消，仍可确认原结果。
- 取消后重试只返回已取消订单，不会重新创建订单或再次消费。原有订单状态机和一次退款保护保留。

订单、余额扣减与消费流水在同一数据库事务中提交，写流水失败时整单回滚。订单保存提交者类型和编号，区分customer与staff命名空间；员工1号与会员1号不是同一提交者。数据库对非空请求编号建立唯一索引，历史订单可继续保留NULL。

## 结果确认

`GET /orders/requests/:requestId` 返回原提交者的订单结果，其他提交者或尚无结果返回404，无关岗位403。查询也通过当前SQLite进程内事务队列，避免读取本连接内可能回滚的未提交订单。

**查询404不能证明订单失败。** 原请求可能还在传输或执行，应保留原编号查询或同参数重试。不能另建编号重复付款。同一编号的结果确认与所有订单列表查询职责不同：顾客列表可看到本人订单，财务岗位列表可履约处理门店订单。

## 顾客端恢复

`useOrderRequest` 在发送前按会员ID将原编号与商品参数写入本标签页sessionStorage，双击共用在途请求。网络超时后查询原订单；结果未知时保留记录、锁定购物车并提供“确认原订单”。刷新或切换页面后恢复原参数，已经下机或购物车为空仍能确认原订单。

明确的提交400/404允许修改输入；401/403/409/5xx或查询失败继续保留原记录。存储写入失败、损坏记录或账号变化不允许静默发起新扣款。同一会员资料刷新保留在途流程，避免因替换会员资料对象重建请求。订单确认成功与资料刷新分开提示，资料刷新失败不显示为下单失败；已取消的原订单显示退款状态。

该恢复范围仅限本标签页，关闭标签页或手动清存储后，应先核对订单。不同标签页、设备或人员为同一现实点单创建不同编号，本机制不能自动判断为重复。当前未设计跨设备收款单或支付对账。

## 数据库和验证边界

增量迁移位于 `backend/src/database/migrations/1792543800000-OrderRequestId.ts`，为旧订单增加可空请求编号、指纹与提交者字段，以及唯一索引。已在独立内存SQLite旧表中验证原数据保留；本轮没有对用户数据库执行迁移。当前本地配置仍有TypeORM自动同步，完整PostgreSQL迁移治理在后续迭代中。

定向回归包括并发重试、异参冲突、提交者隔离、原价格快照、取消退款后重试、整单回滚、未提交结果隔离、旧表迁移和顾客页面实际接入。不代表多实例余额并发安全、真实支付、跨进程重启或浏览器人工验收。前后端需同时使用新格式，原服务需重启才加载此次变更。
