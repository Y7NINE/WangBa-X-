# 低余额结算边界

当前本地规则：正常会话按开始分钟向上取整、金额四舍五入到分；余额足够直接结算，重复确认只记一笔消费。余额不足时采用“固定账单、停计费、保留占用、补款后完成”的流程，不部分扣款、不自动透支或减免。

## 待结算状态

首次不足额的 `PATCH /billing/sessions/:id/end` 在事务中保存结算申请时间、时长和金额，将会话暂停。返回409时，这一暂停及固定账单已经提交；不能在事务中抛异常让停计费状态一起回滚。示例错误正文：

```json
{
  "code": "SETTLEMENT_PAYMENT_REQUIRED",
  "sessionId": 9,
  "amount": 2,
  "balance": 0.5,
  "shortfall": 1.5,
  "message": "已停止计费，账单¥2.00，还需补款¥1.50后重试结算；座位暂保留占用"
}
```

会话保留 `status=paused`，新增 `settlementRequestedAt` 区分普通暂停和已申请结算；既有查询及座位占用检查继续生效。该时间、`duration`和`amount`写入会话表，后续重试和查询使用同一账单，不再根据等待时长或新费率增长费用。原本已暂停的尾部等待也不收费。

本规则只在主动申请结算时止计费；没有实现余额耗尽自动断网、硬件锁屏或自动下机。座位在财务结清前继续占用，不会因为账单固定就变为空闲，也不提前创建保洁。前台须处理补款和结算，避免长期占座。

## 补款与完成

补款沿用充值请求编号幂等流程。补足后再次调用原会话结算：以固定金额按分比较余额、一次扣款、记录消费流水、完成原会话，再根据故障状态释放为待保洁或故障座位。并发或重复结算不重复扣款、创建保洁或广播释放状态。

最终 `endTime` 为原结算申请时间，表示停止计费的时间；若原本暂停，会累计申请前的尾部暂停时长。保洁任务的创建时间为实际财务结清、释放座位的时间，不能沿用更早的计费截止时间。

待结算期间不能恢复计费、创建新点单或唤醒、通过故障换机继续使用。充值、退款和原订单结果确认仍可进行；已经成功的旧订单重试不会因会话待结算而新扣款。不能另起上机会话或由别人抢占原座位。

## 页面行为

管理端显示“待结算（已停计费）”，隐藏恢复按钮，提供重试结算；欠费或网络错误后重新读取会话，结算成功但列表刷新失败分别提示。顾客个人中心显示待结算和“补款后重试结算”；失败后读取服务器固定账单，网络查询失败保留已知会话。结算已经确认时，资料刷新失败不会变成结算失败。顾客点单页阻止新增购物车，保留原订单确认入口。

补款不会自动恢复使用或自动完成结算。须显式重试结算，之后若继续使用，重新选择可用座位开始新会话。

## 数据与验证边界

增量迁移为sessions增加可空 `settlement_requested_at`；历史会话保持NULL。本轮只在独立内存SQLite旧表上执行验证，没有操作用户演示库。保留现有SQLite进程事务队列；PostgreSQL和多实例并发仍需后续验收。

回归使用可控时钟覆盖等待后金额不变、原暂停尾段、恰好足额/分币/零费率、分钟边界、补款后并发确认、跨业务继续使用限制、流水失败整笔回滚及旧表迁移。尚未做真实设备停止使用、浏览器人工验收、进程重启恢复或生产迁移。前后端需同版本并重启原服务才加载变更。
