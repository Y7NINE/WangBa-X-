# 充值请求与结果确认

适用于当前本地 SQLite 仿真。前台记账接口不调用真实微信、支付宝或银行卡收款服务，支付方式字段只是记账分类。

## 接口约定

`POST /billing/recharge` 限店长、经理和收银，示例请求：

```json
{
  "requestId": "a03f9fd2-24e9-4ba7-883c-a3760f9c8b15",
  "userId": 7,
  "amount": 12.34,
  "paymentMethod": "cash"
}
```

一笔新充值创建一个 UUID v4。超时、断网或重复点击必须保留原编号、会员、金额和支付方式。服务端将编号统一为小写，并由登录身份记录操作员。

- 原操作员使用同编号、同参数重试：返回原交易流水，余额只增加一次，响应仍为201。
- 同编号用于不同会员、金额、支付方式或操作员：409，不产生新入账。
- 请求编号缺失或不合法、输入不合法：400。会员不存在：404。
- 编号、流水与余额变更在同一数据库事务中提交；失败时一起回滚。
- 返回的 `balanceAfter` 是该笔流水的历史余额快照。后续消费或充值可能已改变当前余额，应刷新会员资料取得最新余额。

`GET /billing/recharges/:requestId` 仅允许原操作员查询，返回已记录的充值流水。其他操作员或暂无记录返回404；无关角色403。当前SQLite实现把结果查询也放入同一进程的事务队列，避免将本连接内尚未提交、仍可能回滚的结果提前当作成功。

**查询404不能证明充值失败。** 原请求可能尚未到达或仍在执行；应保留原编号查询或按原参数重试，不能另建编号再次收款。不能因为请求超时就让会员重新付款。

## 两个页面的恢复行为

计费管理和会员管理共用充值流程。请求发出前在 `sessionStorage` 中按操作员保留编号和参数，同标签页切换页面或刷新后可恢复。确认成功才清除；提交明确返回400/404时允许更正输入。结果未知、403/409/5xx时保留原记录，锁定参数，提供“确认结果 / 重试原充值”。其他会员有待确认记录时，先到计费管理处理该记录。

超时后先按原编号查询，找到匹配流水即确认成功；查询无结果或失败继续保留。余额来自服务端流水，随后刷新资料，不在旧余额上再次累加。请求确认期间不提前显示“充值失败”，避免误导重复收款。

该恢复范围是当前标签页。独立标签页、不同设备或不同操作员新建不同编号的同一笔现实收款，不能依靠本机制自动识别。关闭标签页或手工清除浏览器存储后，应先核对已有流水，不能直接新建充值。后续跨设备收款单和真实支付对账需要独立业务设计。

## 数据库与验证范围

`transactions.request_id` 为可空的36字符字段，有唯一索引 `UQ_transactions_recharge_request_id`。历史及非充值流水保留NULL，可继续并存。增量迁移位于 `backend/src/database/migrations/1792542600000-RechargeRequestId.ts`，增加字段和索引，保留旧记录。当前本地配置仍使用TypeORM同步；本轮没有对用户数据库执行迁移或重启服务。

隔离内存SQLite验证包括请求重放、并发重试、异参冲突、原操作员查询、流水失败时余额回滚、数据库唯一索引，以及从旧流水表执行增量迁移保留原记录。管理端测试覆盖刷新恢复、查询404保留、参数锁定、账号切换、存储失败、双击、超时结果确认和两个页面实际接入。

这些检查不代表真实支付、浏览器人工验收、服务进程重启恢复或多实例余额并发验收。PostgreSQL真实迁移、跨进程锁和扣款约束仍在后续清单中。
