# Socket鉴权与授权订阅

本轮完成实时连接的身份和订阅边界。HTTP与Socket通过同一个TokenModule使用JWT配置；连接仍使用 `/socket.io`。原有座位推送事件名不变。

## 握手与身份有效性

客户端通过 `auth.token` 传递JWT。服务端验证HS256签名、有效期、有效的安全正整数主体和已知角色；令牌须有到期时间。顾客还须在数据库中存在且未停用，员工须存在且当前岗位与令牌一致。顾客1号与员工1号分别查询会员、员工表，不混用身份。

缺失、伪造、过期、无到期时间、主体异常、未知角色或与数据库不符的身份在握手阶段收到 `connect_error: UNAUTHORIZED`，不会成为已连接的业务订阅者。静默连接也会在JWT到期时断开；每个入站事件和每次业务推送前重新校验当前身份，会员停用、员工删除或岗位变更后，不继续投递敏感事件。

当前员工表没有独立的账户启停字段，`isOnDuty`表示值班状态，不能把未值班当作账户停用。员工启停管理和HTTP旧令牌即时失效仍需后续完善；本轮身份重查针对Socket。

## 订阅协议

已认证连接默认加入不含个人资料的座位状态流。其他流使用事件 `subscribe`，只接收 `{ "topic": "tickets" }` 这样的单一topic字段；返回 `{ "ok": true, "topic": "tickets" }` 或错误结果。服务端决定房间，客户端不能提交room、userId或staffId，也不能通过自行发送join切换到他人房间。

| topic | 顾客 | 店长/经理 | 收银 | 技师 | 保洁 |
| --- | --- | --- | --- | --- | --- |
| machines | 座位状态 | 座位状态 | 座位状态 | 座位状态 | 座位状态 |
| tickets | 本人报修 | 门店工单 | 门店工单 | 门店工单 | 拒绝 |
| orders | 本人订单 | 门店订单 | 门店订单 | 拒绝 | 拒绝 |
| notifications | 拒绝 | 管理通知 | 拒绝 | 拒绝 | 拒绝 |

订阅权限与实际业务通知接入是两项工作。orders目前只建立授权范围，尚未添加订单推送；第11–12轮已接入工单创建、接单、维修完成和换机。顾客页面展示及恢复、其他工单状态和订单通知仍待完善，不能据此宣称全部通知链路完成。

`machine_status_update`只向已认证座位订阅者投递。`ticket_update`不再全局广播；定向 `new_alert` 仅允许工单岗位，管理 `notification` 仅管理岗位。心跳只确认连接，不能改座位状态；Socket `fault_alert`要求改用已鉴权HTTP报修，不能制造业务工单或广播。所有推送发送前重查身份，数据库校验失败时停止向该连接投递。

## 工单创建和接单（第11轮）

- HTTP报修事务提交后，先发送座位状态，再读取已提交工单，向已订阅工单的员工发送完整 `new_alert` 快照，沿用管理端现有插入与提示流程；本人顾客订阅收到 `{ id, updates: 工单快照, timestamp }` 的 `ticket_update`。员工报修不会因为员工ID与会员ID相同而投递给该会员。
- HTTP接单提交后发送 `ticket_update`，updates仅包含status、handlerId、acceptedAt和updatedAt，分别送达工单岗位和实际顾客报修者的订阅。重复接单仍返回状态错误，不重复发送成功事件。
- 事务失败不会发布上述成功事件。推送失败保留HTTP成功和数据库结果，通过列表快照恢复；没有持久化消息、送达保证或跨请求事件序列号。

本轮仅修改后端，顾客页面尚未接入tickets订阅与业务通知展示；本人投递协议通过真实客户端验收，不等于顾客界面已经展示接单状态。管理端沿用现有监听，本轮没有浏览器端到端人工验收。

## 维修完成与换机（第12轮）

维修完成事务提交后发送实际座位状态，再发送本人工单 `ticket_update`，updates包含status、resolution、resolutionNote、resolvedAt、resolvedBy和updatedAt。有上机会话时座位回online，无会话且没有其他待处理故障时进入dirty并创建保洁任务；既有多故障判断保持不变。

换机提交后按原座位fault、目标座位online顺序发送座位事件，再发送工单status、newMachineId、playerAction、transferredAt、transferredBy和updatedAt。原工单保持accepted，待原座位维修完成；没有把换机当作故障已修复。发送仍按工单岗位和实际报修人订阅隔离，其他会员与保洁不收到工单详情。

其他技师处理拒绝、欠费待结算换机拒绝及事务中途失败均不发送成功事件。推送异常仍以已提交的HTTP状态为准，没有增加持久化送达保证。顾客座位/会话页面在换机后的主动补偿尚待接入。

## 双端连接

管理端握手回调读取当前令牌，重复连接先断开旧连接、移除旧监听；退出或换账号处理旧连接，迟到的旧事件不能修改新连接状态或座位。技师等工单岗位连接后申请tickets订阅，保洁不申请。连接失败显示离线。

顾客首页和选座页共用连接方法；游客不发起匿名连接，仍可使用公开HTTP页面和刷新。登录、退出和换账号时替换连接，握手读取当前store身份，避免清store但尚未清本地存储时重连旧账号。保留已有连接成功后刷新座位的行为；顾客完整业务状态补偿与通知去重仍待后续实现。

管理端第10轮增加区域、座位和工单列表的重连快照补偿。工单岗位先等待订阅成功ack，再拉工单快照，保洁不读取工单；初始化和补偿的同类查询在途去重。快照请求期间收到的座位状态、工单新增/修改/删除会合并到返回列表，避免快照覆盖新事件。同ID工单合并而非重复插入，变化记录在请求结束后释放。

断线使旧请求失效并保留已知快照，换账号/退出则清除缓存。令牌、员工ID或岗位不匹配的旧响应不落入当前数据；同身份资料刷新不重建请求。仅浏览器存储令牌改变时，旧界面查询也会被阻止并提示重新进入账号。部分刷新失败或订阅未确认提供“重新同步”，旧同步失败不能修改新同步完成状态。

这部分在第10轮经过管理端121项测试和构建验收，其中新增16项受控异步/模拟Socket竞态与界面重试回归；第11轮未重跑前端测试或浏览器人工断线。它不包括订单/保洁页面恢复、顾客业务状态补偿、持久化事件重放或跨服务事件序列号，不能宣称完整离线消息恢复。

## 复现与限制

先安装backend、frontend工作区依赖，再执行：

```powershell
npm run test:socket --prefix backend -- --no-cache --silent
npm run test:security --prefix backend -- --no-cache --silent
```

Socket测试单独启动127.0.0.1随机端口与内存SQLite，使用真实Socket.IO WebSocket客户端，不替换网关、JWT或订阅处理。测试客户端复用已安装的 `frontend/node_modules/socket.io-client`，不要求另下载依赖；单独安装backend无法运行这一跨工作区检查。业务244项测试仍保留原Socket替身，二者结果分开记录。

第9轮28项真实连接检查覆盖拒绝握手、角色矩阵、非法房间/他人身份注入、本人工单投递、通知岗位限制、伪造事件无业务副作用、入站及发送前身份重查、过期静默断开和定向告警隔离。它们不代表浏览器人工验收、轮询传输、反向代理、Redis多实例、真实网络断线补偿或完整业务通知验收。

第11轮扩展为37项真实Socket检查，新增9项实际HTTP报修/接单与Socket联动检查：顾客报修后接单、员工/顾客同编号隔离、未订阅员工、重复接单、三种角色越权、两类事务故障回滚及推送失败后的HTTP列表恢复。全部37项、原有244项隔离业务检查和后端构建通过。首次新增检查因Supertest默认导入不兼容失败，改为CommonJS导入后全部通过，未放宽断言；最后增加报修到接单的连续链路后再次通过37项。测试触发器只存在于内存库。

第12轮最终47项真实Socket检查、244项隔离业务检查及后端构建通过。新增10项覆盖有/无会话维修与重复完成、换机后继续维修原座位、其他技师越权、保洁插入/换机工单写入阶段回滚、欠费待结算换机拒绝、两种推送失败后的HTTP状态恢复。检查真实事件内容、投递对象及数据库结果；未修改或重跑前端，未做浏览器人工验收。

当前发送会逐连接重查数据库，适合本地规模验证；多实例性能、共享会话和事件持久化仍在后续清单。JWT退出即撤销、硬件客户端身份、完整生产密钥策略也没有在本轮完成。演示库和原运行服务未改动，需同版本前后端重启后加载当前协议。
